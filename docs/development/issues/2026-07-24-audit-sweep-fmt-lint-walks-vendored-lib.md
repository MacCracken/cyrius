# `cyrius audit` fmt/lint-walks the consumer's vendored `lib/`, so the sweep FAILs on dependency code the project cannot fix

**Discovered:** 2026-07-24 while running the mandated `cyrius audit` step of stiva's dev loop
**Severity:** Medium — hard, permanent failure of a gate consumers are told to run; workaround is
"stop trusting the gate", which is worse than the bug
**Affects:** cycc 6.4.72 and 6.4.76 (confirmed on both; almost certainly since `audit`'s v6.2.25
project-sweep rewrite)
**Consumer:** stiva (reproduced identically in sandhi's layout)

## Summary

`cyrius audit`'s fmt stage reports `FAIL: files need reformatting (cyrius fmt -w)` on a project
where **every file the project owns is already correctly formatted**, and where running the
suggested remedy changes nothing the project can keep.

The cause is that `_audit_sweep` walks `lib/` as if it were project source. In the **cyrius repo
that is true** — `lib/` is the stdlib, 106 tracked files. In **every consumer it is false**:
`lib/` is dependency code vendored by `cyrius deps` from the manifest, and it is gitignored
precisely because it is reproducible rather than authored. stiva and sandhi both have **0 tracked
files** under `lib/`.

So the sweep formats-checks other people's bundles, finds 7 of them unformatted, and blames the
consumer. The advice it prints is actively harmful: `cyrius fmt -w` would rewrite vendored files
that the next `cyrius deps` overwrites — and, in stiva's case, would silently break the
`cyrius deps --verify` lockfile hashes.

This is the shape that hides best: **correct in the cyrius repo, wrong in every project that
consumes it.** The sweep's own docstring says it "works in ANY cyrius project", which is exactly
the claim being violated.

## Reproduction

Any consumer project with vendored deps. Using stiva at `3.0.7`:

```console
$ cyrius audit
── fmt ──
  FAIL: files need reformatting (cyrius fmt -w)
── lint ──
  1 lint warnings
── docs ──
  53 undocumented public fns
── tests ──
180 passed, 0 failed (180 total)
...
```

Now check the files the project actually owns — all 41 tracked `.cyr` / `.tcyr` / `.bcyr` /
`.fcyr`:

```console
$ for f in $(git ls-files '*.cyr' '*.tcyr' '*.bcyr' '*.fcyr'); do
      cyrius fmt "$f" --check >/dev/null 2>&1 || echo "NEEDS FMT: $f"
  done
$ # (no output — 41 files checked, 0 need reformatting)
```

And confirm the remedy is a no-op on project code:

```console
$ cp -r src tests /tmp/fmtproof/
$ for f in src/*.cyr tests/*; do cyrius fmt "$f" -w; done
$ diff -rq /tmp/fmtproof/src src && diff -rq /tmp/fmtproof/tests tests
$ # (no differences — `fmt -w` rewrites zero bytes)
```

The failures are entirely in vendored `lib/`:

```console
$ for f in lib/*.cyr; do cyrius fmt "$f" --check >/dev/null 2>&1 || echo "  $(basename $f)"; done
  cmdit.cyr
  libro.cyr
  patra.cyr
  sakshi.cyr
  sigil-mldsa.cyr
  sigil.cyr
  sigil_crypto_scratch.cyr
```

7 of 83 vendored bundles. None is stiva's code; all are regenerated by `cyrius deps`.

The `lib/` asymmetry, stated plainly:

| repo | `git ls-files lib/ \| wc -l` | `.gitignore` | `lib/` is… |
|---|---|---|---|
| cyrius | 106 | not ignored | **its own stdlib source** |
| stiva | 0 | `/lib/` | vendored deps |
| sandhi | 0 | `/lib/` | vendored deps |

## Root cause

`cbt/commands.cyr`, `_audit_sweep` (v6.2.25 project-sweep rewrite):

```cyrius
    # Source dirs to fmt/lint/doc-walk (whichever exist in this project).
    var dirs = vec_new();
    if (is_dir(str_from("lib")) == 1) { vec_push(dirs, str_from("lib")); }
    if (is_dir(str_from("src")) == 1) { vec_push(dirs, str_from("src")); }
    if (is_dir(str_from("programs")) == 1) { vec_push(dirs, str_from("programs")); }
```

`lib` is unconditionally included when the directory exists. The comment says "whichever exist in
this project", conflating *exists on disk* with *belongs to this project* — for a consumer, `lib/`
exists precisely **because** it is not the project's.

The same `dirs` vector feeds the lint and docs walkers (`audit_fmt_walk` / the cyrlint / cyrdoc
walks below it), so the fmt FAIL is the loudest symptom of a wider miscount, not the only one.
The reported "53 undocumented public fns" and "1 lint warning" are also polluted by vendored code
— worth re-checking once the walk is scoped.

*(Speculation, flagged as such: this is likely untested outside the cyrius repo because
`audit --internal=platform-check` — the path cyrius itself exercises — routes to `check.sh`, so
the project sweep's dir selection is only ever exercised where `lib/` happens to be correct.)*

## Proposed fix

Scope the walk to what the project owns. In rough order of preference:

1. **Treat a `lib/` that the manifest populates as vendored.** If `cyrius.cyml` has a `[deps]`
   section (i.e. `cyrius deps` is what fills `lib/`), exclude `lib/` from the sweep. This is the
   semantically correct test — the manifest already knows.
2. **Honor `.gitignore`.** Skip any directory the project ignores. Cheap, general, and matches the
   intent ("reproducible, not authored"). Also fixes the analogous `build/` and `dist/` cases if
   they ever get walked.
3. **Make it explicit in the manifest** — an `[audit] dirs = [...]` key, defaulting to
   `["src", "programs"]` for consumers and letting cyrius itself opt `lib` back in.

(1) or (2) fixes it without any consumer change. (3) is the most flexible but pushes work onto
every project.

**Independently of the fix: the stage should say what it walked.** `FAIL: files need reformatting`
names no file, so the failure is indistinguishable from a real one and cannot be triaged without
re-deriving the walk by hand — which is how this sat unexamined. Printing the offending paths
would have made it self-diagnosing in one run. Compare the release-gate finding
(`2026-07-14-release-gate-cross-os-runs-only-vr01-glob.md`): a gate that does not state its own
scope reads as authoritative when it is not.

## Consumer-side workaround

None that preserves the gate. Options, all bad:

- **Ignore the fmt stage.** What stiva does now. It trains the team to ignore a red gate, and
  masks any *real* formatting regression in `src/`.
- **`cyrius fmt -w lib/*.cyr`.** Silences it until the next `cyrius deps`, and in stiva breaks
  `cyrius deps --verify` — the lockfile hashes the vendored bytes.
- **Delete the vendored bundles that fail.** They are required deps.

stiva's actual mitigation is to run the per-file commands as the real gate:

```bash
cyrius fmt <changed-file> --check
cyrius lint <changed-file>
```

Both are correct and neither touches `lib/`. stiva's `CLAUDE.md` dev loop already specifies these
per-file forms; `cyrius audit` is the aggregate that is unusable.

## Also seen in the same sweep (separate, lower priority)

- **The bench stage never finds the project's benchmarks.** It looks in `benches/` and
  `tests/bcyr/`; stiva's live benchmark file is `tests/stiva.bcyr` (the layout
  `cyrius bench tests/stiva.bcyr` documents and that stiva's `scripts/bench-history.sh` drives).
  Output is `No benchmarks found` on a project with working benchmarks. Non-fatal, so it only
  misleads rather than failing.
- **The tests stage was broken at 6.4.72 and is FIXED at 6.4.76** — it reported
  `compile error` for all five of stiva's `.tcyr` units (undefined `assert_eq` / `assert_neq` /
  `alloc_init` / `assert_summary`, plus a phantom `undefined variable 'Backend'` in
  `src/runtime.cyr`) while `cyrius tests tests/` ran them all green. Recorded here only so the
  6.4.76 improvement is on the record; no action needed.

## Acceptance criteria

- `cyrius audit` in a consumer project with vendored `lib/` reports `ok: format clean` when every
  file the project tracks is formatted.
- Introducing a real formatting error in `src/` still turns the stage RED.
- The fmt stage names the files it is complaining about.
- The docs and lint counts reflect project code only (re-baseline stiva's "53 undocumented public
  fns" after the fix — the true number is lower).
