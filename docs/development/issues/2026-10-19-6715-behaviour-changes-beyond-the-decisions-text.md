each lane's handoff, commits and issues against the decisions — 6.7.15's D1–D70 asked at its open, 2026-10-18, and the two

## Generics

1. **GN-7 — D8 (a), user 2026-10-18:** A pointer field `p: *G<..>` (G a generic struct) now gets every type-argument refusal at the field, once, used or not. That covers a tuple, a slice, `u128`, the scalars that are not type arguments (`u8`..`u64`, `bool`, `f32`), `Result` / `Option` / `Tagged` / `cstring` / `f64v2`, and an enum, as well as D8's unknown name and number. These are the refusals a by-value `b: Box<..>` field already got on the slot-open compiler. `*Box<i64>`, `*Box<i32>` and `*Box<f64>` are unchanged (exit 7).
   - *Before (6.7.14):* Slot-open compiler (04b1013e2): each unused field compiled with rc 0, no diagnostic, and exited 7. Measured fields: `*Box<u8>`, `*Box<(i64, i64)>`, `*Box<E>` (enum declared above), `*Box<[u8]>`, `*Box<u128>`, `*Box<Result>`, `*Box<Option>`, `*Box<Tagged>`, `*Box<cstring>`, `*Box<bool>`, `*Box<f32>`, `*Box<u64>`, `*Box<f64v2>`. The by-value `b: Box<X>` forms of the same arguments were already refused, one error each.
   - *After (6.7.15):* Merged compiler: each is rc 1 with exactly one error at the field, in the by-value field's own words, one column to the right:
     - "unknown type 'u8' as a type argument (...)" (also 'bool', 'f32', 'u64')
     - "a tuple type cannot be a type argument"
     - "'E' is an enum, not a type argument — enum values are i64; write i64"
     - "a slice cannot be a type argument (6.7.8: slices are fn-locals)"
     - "u128 cannot be a type argument (...)"
     - "generic type-args must be a scalar (i8/i16/i32/i64) or a struct; Result/Option/Tagged/cstring/f64v2/f64v4 are unsupported" (for Result, Option, Tagged, cstring and f64v2)
   - *Beyond the text:* D8 (a) names `struct H { p: *Box<Zork>; n; }` and `p: *Box<1>`, that is, an unknown name and a number. The other refusals already applied to a by-value `b: Box<..>` field, but D8's text does not name them.

10. **FE-13 — D2 (a), user 2026-10-18:** In the declaration zone, a later const- or enum-named redeclaration is now the global's value from program start even when the EARLIER declaration of that name is a computed initializer (a call) or an array `= { .. }` list. In other words, the earlier declaration is not a scalar constant spelled by name or `0`. So a read between the two declarations now sees the later constant, as it already did for a literal redeclaration. The earlier call still runs (its side effect stays) and its result is thrown away. (The item said a list is "not a constant". The guide's § Declaring a global twice (6.6.16) calls a list a constant initializer, so the accurate wording is "an earlier computed initializer or array list". What matters is that the earlier constant is not spelled by name or `0`.)
   - *Before (6.7.14):* Slot-open compiler (04b1013e2:build/cycc). Every probe compiled with rc 0 and no diagnostic:
     - O3 `const C = 5; fn f(): i64 { return 3; } var a = f(); var b = a; var a = C; syscall(60, b*10+a);` exits 35 (b == f()).
     - O8 `enum E { A = 7; } var B[1] = { 3 }; var c = load8(&B); var B = A; syscall(60, c*10+B);` exits 37 (c reads the list's 3).
     - The literal twins exit 55 (`var a = 5;`) and 77 (`var B = 7;`).
     - The sink probe (f increments n, result n*100 + b*10 + a) exits 135.
   - *After (6.7.15):* Merged 6.7.15 build/cycc. Every probe compiled with rc 0 and no diagnostic:
     - O3 exits 55 and O8 exits 77, the same as their literal twins (55 / 77 on both compilers).
     - The sink probe exits 155, so n == 1: f still runs once, and its result goes into a sink.
     - Controls that did not change: a computed redeclaration after a named constant (`var a = C; var b = a; var a = f();`) exits 53 on both. `var a = f(); var b = a; var a = 0;` and `var B[1] = {3}; var c = load8(&B); var B = 0;` exit 0 on both, because a `= 0` redeclaration over a computed or list declaration was already the value from program start.
   - *Beyond the text:* D2's question named "every redeclaration whose earlier constant is spelled by name or `0`". Option (a) reads "Every constant redeclaration is the value from program start ... The literal rows are unchanged". Neither names an earlier declaration that is not a constant (a call or a list). The drafts mark this ⚠, pinned by O3 / O8.

11. **FE-15 — none asked in 6.7.15; 6.7.14's D11 (b) applied to struct and tuple literals:** A declaration-zone struct or tuple literal whose elements are all constants (`var p = P { 1, 2 };`, the named form `P { a: 1, b: 2 }`, `var t = (1, 2);`) is no longer stored again at startup. So a call in an earlier initializer that writes the global now keeps its write. This also holds when the call sits between two declarations of the same literal (same bytes). A redeclared literal of other bytes still keeps declaration order. A read between the two declarations sees the earlier literal (b == 1), and a call's write between them is overwritten by the later literal. D2 (a)'s scalar constants do not keep that order.
   - *Before (6.7.14):* Slot-open compiler 04b1013e2 (x86_64). `struct P { a; b; } fn setp(): i64 { p.a = 9; return 0; } var r = setp(); var p = P { 1, 2 }; syscall(60, p.a*10 + p.b);` compiles with rc 0, no diagnostic, and exits 12 (p.a 1: the startup store reset setp's write). The named form `P { a: 1, b: 2 }` exits 12. The tuple form `fn sett(): i64 { t.0 = 9; return 0; } var r = sett(); var t = (1, 2);` exits 12. The same-bytes pair `var p = P{1,2}; ... var r = setp(); var p = P{1,2};` exits 12.
   - *After (6.7.15):* Merged 6.7.15 build/cycc (x86_64). The same four probes compile with rc 0, give no diagnostic, and exit 92 (p.a 9: setp's write kept). The other-bytes controls do not change. `var p = P{1,2}; var b = p.a; var p = P{3,4}; syscall(60, b);` exits 1 on both compilers. `var p = P{1,2}; var r = setp(); var p = P{3,4};` exits 34 on both: the later literal overwrites the write. The scalar D2 (a) control does change. `const C = 5; const D = 3; var a = D; var b = a; var a = C; syscall(60, b);` goes from 3 to 5, so the literal ordering differs from D2 (a)'s scalars. The scalar analog `var a = 1; var r = seta(); var a = 1;` exits 9 on both.
   - *Beyond the text:* 6.7.14's D11 asked about a scalar global ("a global whose constant initializer folds to zero, or names an enum constant": "(b) Use the folded value"). 6.7.15's D2 names scalar constants. No decision names a struct or tuple literal. The literal-versus-D2 ordering is filed for the user as 2026-10-18-struct-tuple-literal-redeclaration-order-vs-d2.md (6.7.16), but 6.7.15 already ships this value change.
