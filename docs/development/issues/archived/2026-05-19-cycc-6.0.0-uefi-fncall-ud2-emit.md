# cycc 6.0.0 emits `ud2 ud2` at every `fncallN` site for `CYRIUS_TARGET_EFI=1` builds

> **RESOLVED — v6.0.46 (2026-06-03).** Bug 1 (fnptr.cyr not resolving
> under `CYRIUS_TARGET_EFI=1`) was already fixed during the v6.0.x cycle:
> the `CYRIUS_TARGET_EFI ⇒ CYRIUS_TARGET_WIN` predefine implication was
> restored, so `lib/fnptr.cyr`'s MS-x64 `fncallN` bodies emit again and no
> `ud2` sentinel is produced. A v6.0.3-entry premise-check confirmed the
> symptom (ud2 at fncallN under EFI) no longer reproduces. v6.0.46 LOCKS IT
> IN with a regression guard so it can never silently rot again:
> `programs/efi_fncall_probe.cyr` exercises `fncall1..fncall5` under
> `CYRIUS_TARGET_EFI=1`, and `_efi_emit_gate` (programs/check.cyr) byte-scans
> the emitted PE for the `0F 0B 0F 0B` (`ud2 ud2`) pair and FAILs if present.
> Two check.sh gates now cover this end-to-end: "EFI Application emit …
> fncallN emit no ud2 (2026-05-19 UEFI guard)" and "fncall1 resolved via
> $HOME/.cyrius/versions/<v>/lib/fnptr.cyr (no ud2 sentinel)". Closes the
> "gates don't cover the EFI path" gap called out in recommendation #4.
> Bug 2's broader posture (driver should exit non-zero on ANY unresolved
> call, not just emit a ud2 sentinel) is left as-is by design — the sentinel
> remains a deliberate debugging aid; the EFI path that mattered is guarded.
>
> **Filed**: 2026-05-19 (agnosticos side — cyrius agent please pick up and move into `cyrius/docs/development/issues/` when triaged)
> **Severity**: Hard regression — produces silently broken UEFI binaries
> **Last-known-good**: cc5 v5.11.x (state.md "QEMU PASS 2026-05-19" for 1.30.11 was the cc5 v5.11.69 cut before today's cycc-rename ceremony)
> **First-bad**: cycc v6.0.0 (cycle opened 2026-05-19; today's cc5→cycc rename)
> **Reproduces with**: gnoboot 0.2.0 (HEAD `461e1c7`), agnos 1.30.11, OVMF (edk2-ovmf, Arch package, 2026-02 vintage)

## Symptom

`gnoboot` (sovereign UEFI bootloader) built with cycc 6.0.0 panics OVMF with `#UD - Invalid Opcode` before printing its banner. The crash RIP points inside `gnoboot`'s `.text`, at the very first UEFI service call site (`HandleProtocol` for `EFI_LOADED_IMAGE_PROTOCOL` — main.cyr:202).

The OVMF dump:

```
!!!! X64 Exception Type - 06(#UD - Invalid Opcode)  CPU Apic ID - 00000000 !!!!
RIP  - 000000000E069345, CS  - 0000000000000038, RFLAGS - 0000000000010202
...
CR0  - 0000000080010033
CR4  - 0000000000000668
!!!! Find image based on IP(0xE069345) ImageBase=000000000E068000, EntryPoint=000000000E069000 !!!!
```

`RIP - EntryPoint = 0x345`. Disassembling the gnoboot PE32+ at that VA:

```asm
;; Setup for fncall3(fn_hp, handle, &li_guid, &li_out) — MS x64 ABI
140001325: movabs $0x140006110, %rax   ; arg2: handle
14000132f: push   %rax
140001330: movabs $0x1400061b0, %rax   ; arg1: fn_hp (UEFI BS->HandleProtocol)
14000133a: push   %rax
14000133b: pop    %r9                  ; arg4 → r9
14000133d: pop    %r8                  ; arg3 → r8
14000133f: pop    %rdx                 ; arg2 → rdx
140001340: pop    %rcx                 ; arg1 → rcx
140001341: sub    $0x20, %rsp          ; MS x64 shadow space
140001345: 0f 0b                       ; ud2  ← #UD HERE
140001347: 0f 0b                       ; ud2
140001349: 90                          ; nop
14000134a: add    $0x20, %rsp          ; shadow space cleanup
14000134e: mov    %rax, -0x48(%rbp)    ; capture "return value"
```

That's textbook MS x64 ABI call scaffolding with the `call` instruction itself replaced by `ud2 ud2 nop` (4 bytes — same byte count as `call rel32` = `e8 + 4-byte displacement`).

**32 `ud2` instructions (16 paired sites) found across gnoboot's `.text`**, each at a `fncallN` invocation. Every UEFI service call gnoboot makes is `ud2`-bombed.

## Diagnosis

Two interlocking bugs:

### Bug 1 — `lib/fnptr.cyr` does not resolve under cycc 6.0.0 for `CYRIUS_TARGET_EFI=1`

gnoboot/src/main.cyr:20 has the canonical include:

```cyrius
include "lib/fnptr.cyr"
```

The file exists in `~/.cyrius/versions/6.0.0/lib/fnptr.cyr` (51 KB, identical-or-newer than v5.11.69's copy — same `fncall0..fncall8` definitions). But cycc 6.0.0 emits "undefined function 'fncall1'..'fncall5'" warnings, indicating the include resolved no body for them.

Per the fnptr.cyr docstring:

```
x86_64 MS x64 (CYRIUS_TARGET_WIN — Windows AND, since v5.11.52,
               CYRIUS_TARGET_EFI implies this branch):
```

So the body-emission depends on `CYRIUS_TARGET_EFI=1` implying `CYRIUS_TARGET_WIN`. **It's likely this implication did not survive the cycc rename.** Either:
- (a) `CYRIUS_TARGET_EFI=1` no longer auto-defines `CYRIUS_TARGET_WIN` in cycc 6.0.0, so fnptr.cyr's `#ifdef CYRIUS_TARGET_WIN` body is skipped, OR
- (b) The stdlib-include resolution path for `"lib/fnptr.cyr"` lost its `CYRIUS_TARGET_EFI`-conditional handling.

The state.md historical note "v5.11.52 note: under CYRIUS_TARGET_EFI=1, cyrius predefines BOTH CYRIUS_TARGET_WIN AND CYRIUS_TARGET_EFI" is the load-bearing invariant. Whatever ensured that predefine in cc5 v5.11.52..v5.11.69 has either regressed or moved under cycc 6.0.0.

### Bug 2 — cycc emits `ud2 ud2` placeholders for undefined-function calls instead of failing the build

When cycc encounters a call to a function it cannot resolve, the correct behavior is to fail the build (or at minimum, fail the link step). Instead, cycc currently:

1. Emits a warning ("undefined function 'X'").
2. Emits a warning ("call site may be unreachable").
3. **Emits `ud2 ud2 nop` in place of the `call` instruction.**
4. Returns 0 from the compiler driver.

This is a sentinel pattern that's useful for debugging — the resulting binary, if executed, will trap at the broken instruction with a recognizable signature. But shipping that binary as "OK" is a footgun: it produces silently-broken artifacts that look like successful builds. The smoke test `tests/ovmf_smoke.sh` correctly catches it; but in a less-instrumented pipeline (e.g., a CI that only checks exit codes), this regression slips through.

Suggested fix posture: **the `ud2` sentinel is fine, but the driver should exit non-zero when ANY unresolved-call site is emitted.** A `--allow-undefined-calls` opt-in flag could preserve the current behavior for debugging.

## Workaround attempted — none yet

Cannot work around in consumer code: the include statement is correct, the stdlib file is present, the build invocation matches docs. The issue is in cycc 6.0.0's stdlib-resolution + define-propagation chain, not in gnoboot's source.

A `vendored lib/fnptr.cyr` copy in gnoboot/lib/ might dodge the resolution path, but doesn't fix the `CYRIUS_TARGET_EFI` predefine breakage (the file still needs `CYRIUS_TARGET_WIN` to fire). And vendoring would be a workaround to mask a compiler regression, not a real fix.

## Blast radius

| Consumer | Status |
|---|---|
| `gnoboot` (v0.2.0) | broken — first call into UEFI BS = #UD |
| any future UEFI app built with cycc 6.0.0 | same — `fncallN` is the only way to call UEFI services from cyrius |
| `agnos` kernel | unaffected at build time (no `fncallN` — kernel uses raw asm for boot services), but **untestable in QEMU** until gnoboot is fixed because gnoboot is the only loader on Path C (GRUB-MB2 is dead per the W^X blocker) |
| `tarang`, `daimon`, anything that uses `lib/fnptr.cyr` for C-FFI on Linux | depends on whether the **CYRIUS_TARGET_LINUX → SysV branch** of fnptr.cyr also lost its resolution. Worth a parallel test. |

This blocks all post-1.30.11 iron testing for agnos. Iron Attempt 71 (quiet-boot-mode diagnostic — which is what motivated this whole audit) cannot proceed until gnoboot builds correctly again.

## Context — what made today different

Per `agnosticos/docs/development/state.md` (2026-05-19 refresh):

> **Cyrius v6.0.0 cycle opened today (2026-05-19)** with the two-binary rename ceremony: `cyrc → cybs` (Cyrius Bootstrap), `cc5 → cycc` (Cyrius Computer Compiler) — ~2,100 occurrences across ~157 files… Back-compat symlinks ship in `~/.cyrius/versions/<v>/bin/` so v5.11.x consumers (agnos 5.11.64, agnosticos/scripts 5.11.59) keep working unchanged.

The binary-name back-compat works. The **stdlib-resolution behavior under the new compiler** evidently does not — at least for `CYRIUS_TARGET_EFI=1` consumers. The rename ceremony's "Mechanical gates at v6.0.0 cut: cycc self-host byte-identical at 874,240 B (+8 B vs cc5 at v5.11.69's 874,232 B, from the longer 'cycc' binary-name strings). check.sh 76/76. cyrius test 152/152. 3-step bootstrap" — the gates didn't catch this because they don't include a `CYRIUS_TARGET_EFI=1` build-and-run smoke. gnoboot's `tests/ovmf_smoke.sh` would have caught it if run.

## What I (agnosticos-side agent) recommend the cyrius agent verify

1. **Predefines under `CYRIUS_TARGET_EFI=1`** — what does cycc 6.0.0 set? Specifically: is `CYRIUS_TARGET_WIN` predefined too? Last-known-good was cc5 v5.11.52+ where `CYRIUS_TARGET_EFI=1` auto-predefined `CYRIUS_TARGET_WIN`. Check `src/cybs.cyr` / `src/cycc.cyr` (or wherever predefines live now) for the EFI→WIN implication code.

2. **Stdlib-include resolution for `"lib/fnptr.cyr"`** under cycc 6.0.0. Where does the wrapper search? Does the v5.11.x consumer's `cyrius = "5.11.59"` pin route includes to `~/.cyrius/versions/5.11.59/lib/`, or to the active cycc's `~/.cyrius/versions/6.0.0/lib/`? The drift warning suggests cycc 6.0.0 is in charge regardless of pin.

3. **Driver behavior on undefined-call emit** — change to exit-non-zero by default. The `ud2` sentinel is fine as the emitted instruction (it's a valid debugging aid), but the driver shouldn't claim success.

4. **Add UEFI-emit smoke to v6.0.x gates** — `check.sh` and `cyrius test` clearly don't cover the `CYRIUS_TARGET_EFI=1` path end-to-end; add gnoboot's `tests/ovmf_smoke.sh` (or an analogous minimal-EFI build-and-OVMF-boot test) so this regression class can't ship again.
