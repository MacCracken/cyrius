## Summary

`cyrius distlib --all` writes a `dist/<lib>.deps` sidecar per bundle. Since 6.5.10 the **base**
bundle's sidecar is the declared `[deps] stdlib` **unioned** with an include-scan, specifically so
it cannot under-report. **Profile** bundles kept the older pruned inference — include-scan only.

That inference is incompatible with the convention the toolchain itself documents. From
`docs/guides/cyrius-guide.md:835`:

> Includes are auto-prepended by the build tool — **source files only need project includes.**

A project that follows that advice has **no stdlib include lines in its sources at all**. An
include-scan of those sources therefore finds nothing, and every profile sidecar is written empty:

```
$ cyrius distlib --all
dist/ranga.deps: 25 stdlib leaf requirements
dist/ranga-spectral.deps: 0 stdlib leaf requirements     <-- wrong
dist/ranga-hwaccel.deps: 0 stdlib leaf requirements      <-- wrong
```

```
$ cat dist/ranga-spectral.deps
# cyrius dep sidecar - stdlib leaves this fold requires in scope.
# Auto-generated by `cyrius distlib`; consumed by `cyrius deps`.
```

Two comment lines and nothing else. `dist/ranga-spectral.cyr` is 7,769 lines that need
`alloc`, `math`, `ganita`, `freelist` and 21 more leaves to compile.

The two rules are individually reasonable and jointly produce a guaranteed-empty file. Anyone who
takes the guide's advice gets it.

## Why the existing rationale does not cover this

The profile rule is justified in the guide as avoiding over-report:

> Profiles keep the pruned inference (a profile is a narrow module subset, so unioning the whole
> declaration in would over-report and fail a legitimately-narrow consumer).

That reasoning assumes **the base bundle is the widest and profiles are subsets of it.** That
assumption fails in both directions already in-tree:

- **prakash is inverted** — `[lib]` is the narrow math-only core and `[lib.ai]` is the wide one.
  prakash works around it with a hand-written `scripts/sync-deps-sidecar.sh` whose header comment
  documents the same assumption failing. That script is the existing evidence this rule needs
  revisiting; it predates this report.
- **ranga's profiles are supersets** — each is the full core list *plus one module*
  (`[lib.spectral]` = core + `src/spectral.cyr`). Unioning the declaration in would be exactly
  right here, and would never over-report, because the profile is a strict superset of the base.

So the "narrow subset" premise holds for neither of the two first-party projects that use profiles.

## Reproduction

Any project whose sources omit stdlib includes:

```toml
# cyrius.cyml
[lib]
modules = ["src/a.cyr"]

[lib.extra]
modules = ["src/a.cyr", "src/b.cyr"]

[deps]
stdlib = ["alloc", "fmt", "io"]
```

```
$ cyrius distlib --all
dist/x.deps: 3 stdlib leaf requirements
dist/x-extra.deps: 0 stdlib leaf requirements
```

The profile is a strict superset of the base and reports fewer requirements than it.

## Root cause (if known)

Not read — reporting behaviour only. The base path unions `[deps] stdlib` with the include-scan;
the profile path appears to take the include-scan alone. The fix is presumably in which of those
two branches a profile takes.

## Proposed fix

Preference order:

1. **Union `[deps] stdlib` into profile sidecars too, then prune against what the profile's modules
   actually reference** — computed from the *bundled source*, not from include lines, which is the
   only signal that survives the auto-prepend convention. This gets prakash's inverted case and
   ranga's superset case both right.
2. **Failing that, union the declaration unconditionally** — same as the base. Over-reporting is
   the strictly safer failure: the guide notes an under-reporting sidecar silently switched OFF
   `cyrius deps`' consumer check, which is the more serious of the two, and prakash's script header
   records that over-declaring resolves cleanly (exit 0) in practice.
3. **At minimum, warn when a sidecar is written with zero leaves** for a non-empty bundle. A
   7,769-line bundle needing nothing is never true, and the generator can see that.

What should not happen is a silently empty published file. Note the diagnostic bar is low: the
generator already knows both the bundle's line count and the leaf count it is about to write.

## Consumer-side workaround (if any)

prakash's `scripts/sync-deps-sidecar.sh` rewrites the sidecars post-hoc. It is ~100 lines of shell
to state something the manifest already declares, and it has to be re-run after every `distlib`.

ranga has not adopted it, because the more useful data point for triage is a second project hitting
this from the opposite direction with no workaround in place. ranga documents the under-report in
its manifest and treats `dist/ranga.deps` as the authoritative list for all three bundles, which is
correct there precisely because its profiles are supersets of the base.

**Severity calibration.** Nothing breaks today — prakash measured (6.5.20) that the sidecar is not
an enforced contract: a consumer declaring fewer folds than listed still resolves cleanly, and a
bogus fold name raises no error. This is filed as Medium rather than Low because the file is
*published metadata describing an artifact*, the guide describes tooling that consumes it, and the
failure is silent in the direction the 6.5.10 fix was specifically made to prevent.
