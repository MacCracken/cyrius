## Summary

The ELF-aarch64 backend renumbers x86-canonical syscall numbers at every `svc` through the ESYSXLAT
chain (`9 → 222` mmap, `39 → 172` getpid, …). The chain does not know about regions. Inside a
native-aarch64 region (`#ifdef CYRIUS_ARCH_AARCH64`, `#ifplat aarch64`, the `#else` of `#ifndef`, which
the preprocessor marks `#@a+` / `#@a-`), a raw literal is the author's NATIVE number by construction.
6.6.12 used that rule to SILENCE the raw-literal warning there. But when the native number is also an
x86-compat row SOURCE, the chain still rewrites it, so a different syscall runs with no diagnostic. The
working spelling is the private alias `1000 + N` (`1009` for lgetxattr, `1039` for umount2), which the
band at the end of the chain maps back to native `N`.

## Reproduction

`docs/development/issues/repros/2026-10-08-aarch64-native-region-literal-translated-silently.cyr`:

```sh
cat src/main_aarch64.cyr | build/cycc > /tmp/cc_a64 && chmod +x /tmp/cc_a64
R=docs/development/issues/repros/2026-10-08-aarch64-native-region-literal-translated-silently.cyr
/tmp/cc_a64 < $R > /tmp/a && chmod +x /tmp/a && qemu-aarch64 /tmp/a; echo $?
# actual:   no warning at compile; exit 22 (mmap(…, flags 0) → -EINVAL)
# expected: a compile-time warning naming the translation and the 1009 spelling
#           (or, if the user so decides, exit 0: native lgetxattr → -ENOENT)
sed 's/syscall(9, /syscall(1009, /' $R | /tmp/cc_a64 > /tmp/a2 && chmod +x /tmp/a2 && qemu-aarch64 /tmp/a2; echo $?   # 0
```

## Root cause

- `src/frontend/parse_expr.cyr:2336` `_sysx_meant_here` returns 0 inside a native region
  (`PP_A64_NATIVE_AT`, `src/frontend/lex_pp.cyr:415`). That is the right answer for the "this is x86
  `<name>`" warning. Nothing asks the reverse question: does this native number have a compat row that will
  rewrite it? The call site is `src/frontend/parse_expr.cyr:3057-3059`.
- `src/backend/aarch64/emit.cyr:1293-1749` (the Linux arm of `ESYSXLAT`, `:841`): a raw `EW` chain with no
  query mode, unlike the Mach-O arm (`_macho_arm_routes`, `:1769`, which replays its chain with
  `_esx_qon = 1`). For example the `9 → 222` row is at `:1330` and `39 → 172` at `:1336`; their band
  aliases `1009 → 9` and `1039 → 39` are at `:1738` and `:1714`.
- `_SYSX_MEANT` (`src/common/syscall_xlat.cyr:14`, generated by `programs/gen_syscall_xlat.cyr` from the
  two stdlib peers, not from the chain) does not list 9 or 39, so these rows never warn even outside a
  region. That is intended there, because the x86 meaning is the one applied.

## Proposed fix

Add a warning only, so no program changes behaviour. Inside a native region, when a literal is a SOURCE
of a Linux-arm ESYSXLAT row, warn: "raw syscall N inside a native-aarch64 region is renumbered as x86
`<name>` → M; write `1000+N` for native `<native name>`". Name the alias only when the band has a
`1000+N → N` row. Otherwise say none exists, which is a band addition. Derive "is a row source" from the
chain itself, never a parallel list: give the Linux arm the query mode the Mach-O arm has. One option is
to replay it into a scratch buffer and collect the `cmp x8, #imm` immediates (`0xF100001F | imm << 10`).
`tests/gates/platform/esysxlat_row_order.sh` already reasons about these words. Add the repro as a gate row and a
`tests/tcyr/crossos/` companion for the alias spelling.

Not translating literals inside a region would change what existing programs do, so that alternative is
**the user's decision**.
