# `memmove` — an overlap-safe copy in `lib/string.cyr`

**Filed:** 2026-10-14 from agnostik 1.10.0 (in flight: the OTLP encoders' in-place protobuf buffer)
**Status:** 🟡 **PROPOSED** — a missing stdlib primitive with measured consumer workarounds, not a capability gap.
**Placement:** later in the 6.7.x line — after Break 2 (6.7.11 – 6.7.15) and the 6.7.16 audit; its release is set when the review follow-ups are (the user, 2026-10-15: "keep proposals for later in 6.7.x line").
**Severity:** Quality-of-life, with a latent-correctness edge. Nobody is blocked: every consumer that moves bytes
within one buffer hand-rolls a backward loop, or relies on `memcpy` copying forward, which its comment does not
promise.
**Affects:** `lib/string.cyr` only: one new fn beside `memcpy`, plus one sentence in `memcpy`'s comment. No compiler,
IR or backend change, so every target inherits it.

## Summary

The stdlib has `memcpy(dst, src, n)` and `memset`, but no copy that is correct when the source and destination
overlap. `memcpy` is a forward byte loop (`lib/string.cyr:61`). For an overlapping shift **right** (`dst > src`) it
smears the first bytes across the range, so every consumer that opens a gap in a buffer writes its own backward
loop. This proposal asks for:

```cyrius
# Copy n bytes from src to dst; correct for any overlap. Returns dst.
fn memmove(dst, src, n): i64
```

C (`memmove`), Rust (`ptr::copy`) and Go (`copy`) all provide this primitive. No repo under `~/Repos` defines
a `memmove` today, so the name is free in the flat namespace.

## Motivation — the hand-rolled copies

A scan of `~/Repos` (excluding vendored `lib/`, `build/`, `dist/` and archives) for `while` loops that decrement an
index and `store`/`load` through it finds **14 plain overlapping shift-right copies in 10 repos**. Each opens a gap
in a buffer, which is `memmove(p + k, p, n)`:

| Repo | Site | What it shifts |
|---|---|---|
| patra | `src/btree.cyr:147`, `:210`, `:216` | B-tree node keys and values on insert |
| sankoch | `src/bzip2.cyr:240`, `:319` | move-to-front tables (i64 slots) |
| sankoch | `src/brotli.cyr:846` | brotli MTF: **hand-unrolled to 8-byte chunks**, then a byte tail |
| sankoch | `src/brotli_enc.cyr:837` | brotli encoder MTF, byte loop |
| dhancha | `src/textinput.cyr:226` | the text buffer on character insert |
| puka | `src/grid.cyr:312` | a grid row's glyph and colour cells on insert-chars |
| shravan | `src/mp3.cyr:1924` | the synthesis V-vector history, by 64 slots |
| agora | `src/main.cyr:2406` | leaderboard rows (a `memcpy` per row, walked backward) |
| niyama | `src/nfa_edit.cyr:51` | `_nfa_shift_right`: NFA instructions, 16 bytes; called by all 5 regex engines |
| agnostik | `src/proto.cyr` (`_stik_pb_close`, 1.10.0) | a protobuf message body, to widen its length varint |
| vidya | `content/btree_indexing/cyrius.cyr:66` | the reference B-tree example teaches the same loop |

Two other loops are insertion-sort shifts with an early exit, so they are not plain copies and are left out:
cyrius-yeomans-descent `src/server.cyr:1115` and agnos `tests/waits/waitx.cyr:943`.

**Speed is left on the table.** Every one of these loops except sankoch's brotli decoder moves a byte, or one i64
slot, per iteration. Measured with `cyrius bench` on cyrius 6.7.9, shifting a buffer right by one byte:

| Copy | x86_64 | aarch64 (qemu-user) |
|---|---:|---:|
| byte loop, 64 B | 147 ns | 798 ns |
| 8-byte chunks from the end, then a byte tail, 64 B | **22 ns** | **174 ns** |
| byte loop, 4 KiB | 7.46 µs | 49.6 µs |
| 8-byte chunks, 4 KiB | **0.95 µs** | **6.8 µs** |

sankoch's brotli decoder already hand-unrolls to 8-byte chunks for this reason. A stdlib `memmove` gives every
consumer that speed without each repo re-deriving why the chunked backward copy is correct.

**The implicit contract.** `memcpy`'s comment says "Copy n bytes from src to dst" and says nothing about overlap.
Its forward loop happens to handle an overlapping shift **left** (`dst < src`), so a consumer can come to rely on
that without knowing it. The scan found 22 `memcpy` calls outside `lib/` whose source and destination share a
base. Three were checked and do not overlap given their layouts:
- sigil's `src/ec_ct.cyr:119` copies `nl * 8` bytes 64 bytes down, with `nl <= 6`;
- agora's `src/wager.cyr:544` stays within its 128-byte gap, because `WF_TRACE_MAX = 8`;
- patra's `src/lib.cyr:2021` compacts whole rows.

The other 19 were not audited. But nothing tells the next writer that an overlapping `memcpy` is unsupported, and a faster
`memcpy` (below) would make any such use a silent corruption.

## Proposed semantics — hard rules

1. `memmove(dst, src, n)` copies `n` bytes so that afterwards `dst[0..n)` holds what `src[0..n)` held before the
   call, for **any** overlap of the two ranges.
2. It returns `dst`, the same as `memcpy`, with the same argument order.
3. `n <= 0` is a no-op, matching `memcpy`'s `while (i < n)`.
4. Pure Cyrius, no inline asm: `memcpy`'s comment records why its `rep movsb` block was removed (it broke aarch64
   instruction alignment).
5. `memcpy`'s comment gains one sentence: *the ranges must not overlap; use `memmove` when they may.* Its code does
   not change in this bite.

## Implementation sketch

```cyrius
# Copy n bytes from src to dst, correct for any overlap of the two ranges.
# Copies from the end when dst lies inside (src, src + n), else from the start.
# Returns dst.
fn memmove(dst, src, n): i64 {
    if (n <= 0) { return dst; }
    if (dst > src) {
        if (dst < src + n) {
            var i = n;
            while (i > 0) {
                i = i - 1;
                store8(dst + i, load8(src + i));
            }
            return dst;
        }
    }
    var j = 0;
    while (j < n) {
        store8(dst + j, load8(src + j));
        j = j + 1;
    }
    return dst;
}
```

**Optional second bite: 8-byte chunks.** Backward: `while (i >= 8) { i = i - 8; store64(dst + i, load64(src + i)); }`
then a byte loop for the head. Forward is the mirror image. This is correct for **any** distance between the ranges.
On the backward pass, each chunk's store lands at or above the next chunk's load (`dst > src`), so no byte is
overwritten before it is read; the forward pass is symmetric. The chunks are unaligned. x86_64 allows that, and the qemu-aarch64 measurements above ran
unaligned chunks; native aarch64 and agnos should be confirmed before landing. The same path should speed
`memcpy` comparably (its 4 KiB disjoint copy measured 7.51 µs, the same byte-loop cost), but that was not
measured, and changing a hot primitive every program links is a separate decision.

## Hazards, and what bounds them

- **Name collision.** A consumer with its own `memmove` would be displaced by last-definition-wins. None exists
  under `~/Repos` today.
- **Behaviour change.** None. The fn is new, and `memcpy`'s code is untouched (rule 5 changes only its comment).

## Alternatives considered

1. **Make `memcpy` overlap-safe** (a direction check per call). That costs every `memcpy` caller a compare and
   branch, hides intent, and blocks a future faster forward-only `memcpy`. C keeps the two separate for this
   reason.
2. **A narrower `mem_shift_right(p, n, by)`.** That fits the gap-opening sites, but not a general overlapping copy
   such as agnostik's varint widening. `memmove` is the spelling every systems language uses.
3. **Status quo.** That leaves 14 hand-rolled loops, all but one at byte speed, and the next one written from
   scratch.

## Consumer-side workaround (today)

agnostik 1.10.0's protobuf writer widens a nested message's length prefix in place, shifting the body right by
`k - 1` bytes:

```cyrius
    var i = body;
    while (i > 0) {
        i = i - 1;
        store8(d + mark + k - 1 + i, load8(d + mark + i));
    }
```

With this proposal, that becomes `memmove(d + mark + k - 1, d + mark, body);`.

## Acceptance (proposed gate rows)

- `tests/tcyr/` string rows, comparing each against a copy made through a separate scratch buffer:
  - `memmove` with `dst > src` overlapping, at distances 1, 7, 8, 9 and `n - 1`;
  - `dst < src` overlapping, at the same distances;
  - `dst == src`;
  - disjoint ranges in both orders;
  - `n = 0` and `n < 0`.
- A fuzz row: random `n`, random offsets inside one buffer, checked against the scratch-buffer copy.
- The same rows under `cyrius test --aarch64 <dir>`.
- If the chunked second bite lands: the same rows at lengths 0–33, so every head and tail split is exercised.
